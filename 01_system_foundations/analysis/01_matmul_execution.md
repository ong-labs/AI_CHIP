# 01_matmul_execution.md: Matrix Multiplication & Execution Layer Analysis

이 문서는 [01_matmul_benchmark.py](../lab/01_matmul_benchmark.py) 실습을 통해 확인한 NumPy API의 사용법과 **실행 계층(Execution Layer)** 에 따른 성능 차이의 근본 원인을 분석합니다.

---

## 1. API 사용법 분석

실습 코드에 사용된 주요 NumPy 함수들의 기능은 다음과 같습니다.

* **`A = np.random.rand(N, N).astype(np.float32)`**
  → 0 ~ 1 미만 사이의 값을 가진 N by N 행렬을 생성합니다.
* **`C = np.zeros((M, N), dtype=A.dtype)`**
  → M by N 행렬을 0으로 초기화합니다.
* **`A @ B`**
  → 두 행렬 A와 B의 선형대수적 곱(Matrix Multiplication)을 계산합니다.
* **`np.allclose(C_loop, C_np, atol=1e-3)`**
  → 두 행렬이 허용 오차 내에서 거의 같은 값인지(수치적 동일성) 비교합니다.

---

## 2. 성능의 핵심: 실행 계층 (Execution Layer)

같은 연산이라도 **‘어디서 실행되느냐’에 따라 성능이 수십~수백 배 달라집니다.**

### A. Python for-loop의 한계 (인터프리터 오버헤드)
* **구조**: 3중 루프 (`for i`, `for j`, `for k`)를 통한 $O(N^3)$ 연산 수행.
* **분석**: 문제는 알고리즘이 아니라 **실행 위치**에 있습니다.
* **상세**: 각 연산이 Python 인터프리터 레벨에서 실행됩니다. 이 과정에서 **바이트코드 실행, 타입 체크, 객체 접근**이 매 반복마다 발생하며, 결과적으로 CPU는 유휴 상태에 머물고 Python 언어 자체의 오버헤드가 병목(Bottleneck)이 됩니다.

### B. NumPy의 본질 (Native 레벨 실행)
* **구조**: `A @ B` 연산은 내부적으로 **C / Fortran (BLAS, LAPACK)** 라이브러리를 호출합니다.
* **최적화**: **SIMD, 캐시 최적화, 멀티스레딩**을 활용하며 CPU 벡터 연산을 적극적으로 사용합니다.
* **결과**: 동일한 $O(N^3)$ 복잡도임에도 실행 레벨(Python vs Native)의 차이로 인해 수십 ~ 수백 배의 속도 차이가 발생합니다.

---

### 3.1 실제 측정 데이터 (Execution Results)
$200 \times 200$ 행렬 곱셉(총 16,000,000 FLOPs) 연산 시 측정된 하드웨어 성능 지표입니다.

| 항목 | 실행 시간 (Time) | 연산 성능 (GFLOPs) | 비고 |
| :--- | :--- | :--- | :--- |
| **Pure Loop** | **2.128 s** | **0.0075 GFLOPs** | 인터프리터 병목 현상 발생 |
| **NumPy (@)** | **0.587 ms** | **27.3 GFLOPs** | 하드웨어 자원 극대화 |
| **Speedup** | **3628x** | - | NumPy의 압도적 효율성 증명 |

* **allclose (atol=1e-3)**: **True** (수치적 정확성 확인 완료)

### 3.2 성능 분석
* **이론적 연산량**: 행렬 곱의 연산량(곱셈 + 덧셈)은 $2 \times N^3$으로 계산됩니다.
* **성능 지표**:
  * **Loop**: 실행 시간이 매우 길며, 극히 낮은 GFLOPs를 기록합니다.
  * **NumPy**: 실행 시간이 짧고 높은 GFLOPs를 기록하며 하드웨어 성능을 극대화합니다.
* **allclose 검증**: 성능 비교만으로는 부족하며, 정확도 동일성 검증이 필수적입니다. float32 연산 특성상 발생하는 미세한 오차를 허용하면서 결과의 신뢰성을 확인합니다.

## 4. 결론 (이 실습의 의도)

본 실습은 AI 반도체 및 고성능 연산 분야에서 다음의 인식을 갖추기 위해 설계되었습니다.

1. **Python으로 숫자 연산을 직접 루프로 돌리는 것은 지양해야 합니다.**
2. **벡터화(Vectorization)** 가 연산 성능을 결정짓는 핵심 기술입니다.
3. NumPy는 단순한 편의 라이브러리가 아니라 **HPC 인터페이스**로서 기능합니다.
4. 알고리즘의 복잡도보다 실제 하드웨어에서의 **실행 계층(Execution Layer)** 효율성이 성능의 본질입니다.

### 💡 참고 사항 (Notes)

1. **내부 라이브러리(Backend)**: NumPy의 행렬 연산은 내부적으로 **BLAS(Basic Linear Algebra Subprograms)** 라이브러리(예: OpenBLAS, MKL 등)를 호출합니다. 이는 단순한 코드 최적화를 넘어 CPU의 특성을 극한으로 활용하도록 설계된 결과입니다.
2. **메모리 벽(Memory Wall) 문제**: 루프 방식이 느린 이유는 연산 장치의 속도 문제도 있지만, 캐시를 효율적으로 활용하지 못해 메모리로부터 데이터를 가져오는 데 대부분의 시간을 소비하기 때문이기도 합니다.
3. **아키텍처 설계로의 확장**: 본 분석에서 다룬 '실행 계층의 효율성'은 향후 학습할 **TPU(Systolic Array)**나 **NPU 설계**에서 데이터 흐름(Dataflow) 최적화가 왜 중요한지에 대한 기술적 근거가 됩니다.
